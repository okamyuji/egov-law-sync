# 法律単位フィルターの対応可否調査

## 調査の前提

目的は、法律単位の絞り込みが、現行設計とe-Gov法令APIの制約内で安全に実装可能か判断することです。

完了条件は、ソースコード、設計書、e-Gov公式仕様を突合し、対応可否と限界を提示することとしました。

検証では、CLI、各ユースケース、APIクライアント、テスト、設計書、e-Gov公式OpenAPIを確認しました。今回はコードや設計書を変更しません。

## 判断

ソースコードと公式仕様を突合した結果、対応可能と判断しました。

ただし、法令名を単純な部分一致で指定する実装は安全ではありません。推奨する仕様は次のとおりです。

1. 正規の指定方法として`--law-id`を提供します。
2. `--law-title`も提供する場合は、法令名または略称の完全一致で1件に解決します。
3. 検索結果が0件または複数件の場合は終了コード2を返し、候補を表示して利用者に`--law-id`の指定を求めます。
4. 同じmanifestでは、全件同期と絞り込み同期を混在させません。

想定する利用方法は次のとおりです。

```sh
egov-law-sync bootstrap --law-id 129AC0000000089
egov-law-sync bootstrap --law-title 民法

egov-law-sync bootstrap --law-id 415AC0000000057
egov-law-sync bootstrap --law-title 個人情報保護法
```

「泳法」が文字どおりの指定であれば、e-Gov法令APIの検索結果は0件でした。「民法」の入力誤りを意図していた場合、法令IDは`129AC0000000089`です。

## e-Gov法令APIから確認できたこと

[e-Gov法令API Version 2のOpenAPI](https://laws.e-gov.go.jp/api/2/swagger-ui/lawapi-v2.yaml)によると、`GET /laws`は次の絞り込みに対応しています。

- `law_id`は部分一致で検索します。
- `law_title`は法令名または略称を部分一致で検索します。
- `law_type`や`asof`などの条件も組み合わせられます。

この仕様により、API側で対象を限定すること自体は可能です。

一方、実際に`law_title=個人情報保護法`を指定すると8件が返りました。基本法だけでなく、旧行政機関法、施行令、施行規則なども略称の部分一致で該当します。意図した基本法は次の法令です。

- 正式名称は「個人情報の保護に関する法律」です。
- 略称は「個人情報保護法」です。
- 法令IDは`415AC0000000057`です。

[e-Govの法令種別と法令IDの解説](https://laws.e-gov.go.jp/docs/law-data-basic/607318a-lawtypes-and-lawid/)は、法令IDを法令番号と1対1で対応する識別子として説明する資料です。同じ資料からは、法令名が改正によって変更される場合や、同じ法令名を持つ法令が複数存在する場合も確認できます。このため、永続的な同期対象は法令IDで識別しなければなりません。

[e-Gov法令API Version 1の解説](https://laws.e-gov.go.jp/docs/law-data-basic/8529371-law-api-v1/)によると、更新法令一覧取得APIは指定日に更新された法令の一覧を返します。このAPIには個別法令を指定する条件がないため、アプリ側で選択した法令IDとの積集合を取る必要があります。

実APIで確認した検索結果は次のとおりです。

- `民法`は部分一致で11件が該当し、正式名称が「民法」の法令は1件でした。
- `個人情報保護法`は部分一致で8件が該当しました。
- `泳法`に該当する法令はありませんでした。

## 現行コードから確認できたこと

現行コードには法律単位の絞り込み機能がありません。

- `cmd/egov-law-sync/args.go`には法令を指定するフラグがありません。
- `internal/infrastructure/egov/v2.go`は`/laws`に`limit`、`offset`、`asof`だけを付与します。
- `internal/application/ports.go`の`LawCatalog.ListAll`はフィルターを受け取りません。
- `internal/application/bootstrap.go`は取得した全法令のXMLを対象にします。
- `internal/application/daily.go`は全件一覧との差分を使って異常を判定します。
- `internal/application/weekly.go`は全件bulk zipとmanifest全体を照合します。

`manifest/laws.csv`には、民法と個人情報の保護に関する法律が正しい法令IDで収録されています。

- 民法の法令IDは`129AC0000000089`です。
- 個人情報の保護に関する法律の法令IDは`415AC0000000057`です。

## 推奨する実装方式

推奨する方式は、絞り込みごとに独立した同期範囲を持たせるものです。

法令IDを`bootstrap`、`daily`、`weekly`に渡し、初回に選択した法令IDをmanifestへ記録します。後続の実行で異なるフィルターが指定された場合は、処理を拒否する仕様です。全件manifestと併用するときは、別の`EGOV_MANIFEST_DIR`が必要になります。

取得結果を単純に1件へ絞るだけでは、既存の全件manifestと比較した際に約9,500件が消失判定の対象です。`--force`でこの判定を通すと、全件manifestを1件へ上書きする危険が生じます。そのため、この方法は採用できません。

## 実装上の限界

「個人情報保護法だけ」という指定は、基本法1件を意味します。施行令や施行規則も含める場合は、複数の法令IDを指定できる別の仕様が必要です。

Version 1の更新法令一覧は、日付単位の全件一覧を返す仕様です。アプリは取得後に選択した法令IDだけを残さなければなりません。

週次照合は現在、約324MBの全件zipを使用しており、同期対象を1法令に絞ってもダウンロード量は減りません。

法令名は改称される可能性があるため、永続的な同期キーには法令IDを使います。

フィルターを途中で変更すると、差分、異常判定、前回実行日の意味が変わるため、異なる範囲への変更時は新しいmanifestとして開始します。

既存のGitHub Actionsは法令指定を渡しません。定期的に絞り込み同期を実行する場合は、workflow入力または固定設定も変更対象になります。

## ADRと設計判断

リポジトリには独立したADRファイルがありませんでした。`docs/design.md`の決定表が実質的なADRとして機能しています。

同文書は、次の前提を置いています。

- `laws.csv`は`/laws`全件の写しです。
- 全件数の減少を異常判定に使用します。
- 週次処理は全件zipと照合します。
- 実装を変える前に不変条件を更新します。

完全な1法令だけの同期を実装する場合は、実装前に設計書またはADRで、同期範囲の識別方法、保存方法、途中変更の禁止を決める必要があります。

## 調査時の観測

e-Gov実APIでは、`民法`が11件の部分一致となり、完全一致する民法が1件あることを確認しました。`個人情報保護法`は8件で、`泳法`は0件です。

調査終了時のGit作業ツリーには変更がありませんでした。

コードベースの関係を補助的に調べるためGraphifyを実行しましたが、Geminiバックエンド用Pythonパッケージが不足していたため、意味抽出は終了コード1で失敗しました。新しい依存関係は追加せず、81ファイル、約29,220語の対象から、CLI、アプリケーション処理、e-Gov取得処理、成果物生成、設計判断文書を直接確認しました。この失敗は調査結果に影響していません。

今回は判断だけを行ったため、`go build ./...`と`go test ./...`は実行しませんでした。

## 調査による変更

調査時には、アプリ本体、設計書、依存関係を変更しませんでした。

実装時には、`--law-id`を正規の指定方法とし、`--law-title`を一意に解決できる場合だけ利用できる補助的な指定方法にすることを提案します。

## 未確定事項

依頼にあった「泳法」が「民法」を意味するかは確定していません。ただし、どちらの解釈でも対応可否の判断は変わりません。
